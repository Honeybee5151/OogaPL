## 0. Plain-language summary

1. Open RuneScape private-server projects already contain strong, human-tuned code for the per-tick
   hot paths of an OSRS-style server. Most of it uses permissive licences: rsprot is MIT, rsmod is ISC,
   Lost City is MIT, and the 2004Scape Rust ports are MIT or ISC. 2009scape is AGPL.
2. **The most expensive measured hot path is building each player's "player info" update packet.**
   rsprot reports 170 ms per tick on one thread, or 11.5 ms on 16 cores, for 2,046 players packed into
   a 13×13-tile box, all teleporting and chatting every tick. This is a deliberate worst case from
   April 2024. Lost City reports 86 ms in TypeScript and 35 ms in Rust compiled to WebAssembly (WASM)
   for 2,000 players in one map square.
3. Part of that cost comes from the OSRS protocol itself. Every player's packet walks all 2,047
   player slots, so total work grows with the square of the number of players.
4. **Second is tile pathfinding**: a breadth-first search (BFS) over a 128×128-tile window. A short
   path takes 2.8 µs in native Rust. In Kotlin, an unreachable target takes about 0.37 ms per path.
   Nobody publishes how many paths a real tick computes.
5. NPC info and NPC hunt (aggression) scans rank lower. The NPC info benchmark is "extremely
   unrealistic" in its authors' own words, and nobody benchmarks hunt scans.
6. **Exact correctness checks.** Since July 2026, rsprot has small golden-byte tests. One of them
   checks that multithreaded output is byte-identical. It also has tests that decode the packets back.
   The pathfinding tests check exact routes only for a few cases. The hunt code has no tests of this
   kind.
7. **Speed-ups humans already found:** 13.4% in rsprot PR #76 (2026), after a regression; 40–60 ms
   and "up to 100ms" per tick in Lost City, from rewrites and a Rust port; 2–5× for pathfinding, from
   language ports.
8. **Evidence against:**
   - One 2× micro-benchmark win gave "no noticable improvement" in the end-to-end bot test.
   - The fastest Rust/WASM versions were replaced by TypeScript for platform reasons.
   - A rewrite broke observer behaviour and was reverted.
   - The benchmarks rerun one fixed input, and changing field order alone moved one from 160 ms to
     200 ms.
9. **Money.** Even the worst case is about 0.3 of one core per 2,000-player world, which is roughly
   €1–3 a month on Hetzner (my estimate). This cost is CPU, but it is still small. What it buys is tick
   headroom (bigger worlds) and a credible open benchmark, not euros.
10. **Jagex IP.** The game assets, maps and the cache-derived Huffman table belong to Jagex. rsprot
    says its design follows a US patent publication, and I could not check that patent's status. Use
    synthetic maps, Miles's own protocol, and clean ports of the MIT/ISC code.
11. I found no AI-driven optimisation in these repositories' PR histories.

### 1.2 The player-info algorithm (read from osrs-242 sources)

Files are under `protocol/osrs-242/osrs-242-model/src/main/kotlin/net/rsprot/protocol/game/outgoing/info/playerinfo/`.

- **One update pass per cycle** (`PlayerInfoProtocol.update()`): prepare, then
  `putBitcodes`, `prepareExtendedInfo`, `putExtendedInfo`, `postUpdate`. All steps after prepare run
  per player through a worker.
- **Threading.** VERIFIED from the PlayerInfoProtocol.kt doc comment: "The default worker will remain
  single-threaded if there are less than `coreCount * 4` players in the world. Otherwise, it will use
  [ForkJoinPool] to execute these jobs."
- **High and low resolution.** Each observer keeps a high-resolution list (nearby players, sent with
  full movement and "extended info" blocks such as appearance, chat and hits). It also keeps a
  low-resolution list of everyone else.
  - The client tracks all 2,047 slots. VERIFIED, PlayerInfoProtocol.kt: "as the client tends to
    iterate up to 2048, we cannot often allocate smaller data structures, as that would break the
    client's logic".
  - The test client's `gpiInit` loops `for (idx in 1..<2048)` and puts every other slot in low
    resolution.
  - So **every observer's packet walks about 2,047 slots every tick.** That is about 4.2 million
    observer–slot visits per tick at 2,046 players (GUESS arithmetic: 2,046 × 2,047 ≈ 4.19 M), or
    about 41 ns per visit at 170 ms (GUESS: 170.23 ms / 4.19 M). This is the O(N²) core.
- **Passes per observer** (`pBitcodes`): high resolution with stationary players skipped, then high
  resolution with non-stationary players skipped, then the same two passes for low resolution.
  - Runs of unchanged players are written as a skip count. VERIFIED: "Writes the [count] of
    consecutive stationary players using [run-length encoding]".
  - The skip writer is branchless. VERIFIED comment: "The branching causes a significant (~15-20%)
    performance loss in the extreme end-case benchmarks, so it's best to eliminate it."
- **Movement bitcodes are precomputed once per player, not per observer.** VERIFIED: "High
  resolution bit buffers are cached to avoid small computations for each observer, and it allows us
  to reduce the number of [BitBuf.pBits] calls, which are quite expensive."
  - rsprot issue [#2](https://github.com/blurite/rsprot/issues/2) explains why: "Instead of writing
    2,000 x 2,000 (4 million) bitcodes individually over many bit writes, the 2,000 bitcodes of both
    variants will be pre-computed at the start" (VERIFIED).
- **Extended-info blocks.** Blocks that every observer receives identically are precomputed once into
  buffers and copied with native memcpy. Blocks that differ per observer (some hits, tinting) are
  built on demand.
- **View-range shrinking** (`PlayerAvatar.resize`). VERIFIED doc: "This function will aim to keep the
  number of high resolution avatars at 250 or less."
  - The default range is 15 tiles. When high resolution holds 250 or more, the range drops by 1 tile
    per cycle. After a 10-cycle interval it grows back by 1 tile per cycle.
  - The 250 is soft. VERIFIED: "It is a soft limit and can be exceeded. The default value is 250."
  - "High priority" avatars (for example staff) render out to the preferred range regardless.
  - Lost City uses the same rule (`BuildArea.resize`: `PREFERRED_PLAYERS = 250`, `INTERVAL = 10`,
    `PREFERRED_VIEW_DISTANCE = 15`). VERIFIED,
    [build.ts](https://github.com/LostCityRS/Engine-TS/blob/main/src/network/rsbuf/build.ts).
- **Appearance caching.** VERIFIED, PlayerAvatarExtendedInfo.kt: "An int array to track the last
  cycle during which we recorded other players' appearances. If the values align, the client will
  utilize its previously cached variant."
  - When a player moves from low to high resolution, appearance, move speed and face direction are
    added as observer-specific flags only if this observer's copy is out of date
    (`getLowToHighResChangeExtendedInfoFlags`).
- **Byte budget.** Each packet has `BUF_CAPACITY = 40_000` bytes. If extended info does not fit, it
  is retried next tick. VERIFIED: "due to our buffer being too full to actually write their extended
  info, we need to try again the next tick (and so on) until we finally succeed".
- **TODO and performance comments in the info code** (VERIFIED, osrs-242 model sources):
  - Lookup tables for movement opcodes: "In a benchmark, the results showed ~603% increased
    performance." and "the benchmark showed a 891% performance increase" (CellOpcodes.kt). These are
    micro-benchmarks.
  - Field order matters for the JIT: "due to the field order changing, the performance will
    absolutely tank in doing so, going from ~160ms in the benchmark to around 200ms"
    (PlayerAvatarFactory.kt).
  - NPC observer tracking: "That tracking appears to cause ~13% performance hit in our multithreaded
    benchmark" (NpcAvatarTracker.kt).
  - The only TODOs in osrs-242 main code are unrelated: login (SSL web) and LocMerge.

### 1.3 Is there an exact correctness check?

- **Yes, but small.** PR [#76](https://github.com/blurite/rsprot/pull/76) (merged 2026-07-18) added
  golden-byte regression tests to revisions 235–242, in `PlayerInfoWorldMembershipTest.kt`:
  - `player info packet bytes match baseline across membership transitions` checks against
    `EXPECTED_PACKET_HEX`, 8 recorded packets.
  - `stationary snapshots preserve baseline packet bytes` checks 3 ticks with a handful of players.
  - `parallel observer updates retain baseline packet bytes` reruns the fixture 10 times with
    `ForkJoinMultiThreadProtocolWorker`. **So multithreaded output is checked to be byte-identical.**
  - VERIFIED from code. I did not run the tests.
  - The golden bytes were recorded from rsprot itself, not from Jagex's client or servers. The fixtures
    cover 2–5 players.
- **Decode-back tests.** `PlayerInfoTest` and `NpcInfoTest` feed the packet to a test-side decoder
  (`PlayerInfoClient` and `NpcInfoClient`, written to mirror the client's decoding). They check the
  decoded coordinates and appearance, and `assertFalse(buffer.isReadable)` checks that every byte was
  consumed (VERIFIED). NPC info has decode tests only: 8 tests, no golden hex.
- **Real-client parity is checked by hand.** VERIFIED, issue
  [#41](https://github.com/blurite/rsprot/issues/41) (open), about server packets in general: "This is
  a valuable piece of information that currently has to be obtained by manual verification by myself
  after every revision."
- **Implication (GUESS).** An AI-search harness can extend this pattern: large seeded bot traces,
  golden bytes from a reference port, plus decode-back. The reference would be rsprot's algorithm, not
  Jagex's client.

### 1.4 NPC info algorithm notes

- The server supplies NPCs through zone storage (`ZoneIndexStorage`). The library searches zones
  around the player (`DEFAULT_ZONE_SEARCH_RADIUS = 3`) and keeps the closest ones with top-K arrays
  (`UnsortedTopKArray`).
- **The NPC cap is no longer 250.** VERIFIED, NpcInfo.kt: "Starting with revision 229, on Java
  clients, the limit is 149, and OSRS does indeed only send 149 at most - tested via toy cats. On
  native, the limit is still 250." BENCHMARKS.md's "only supports rendering up to 250 NPCs" describes
  the rev-221 era.
- BENCHMARKS.md also says the benchmark's "index providing is inefficient and costs circa 16%". The
  current benchmark uses `ZoneIndexStorage` instead, so that remark is stale too.

### 1.5 Speed-ups humans found in rsprot (step 3)

- **PR [#76](https://github.com/blurite/rsprot/pull/76) "Perf/cache player world membership"**
  (Khaled431, merged 2026-07-18). VERIFIED body:
  - "With the introduction of world entities, there was some regressions in performance."
  - "Around 13.4% less time spent in player info overall."
  - "Drops world-membership lookups from 7,996,000 to 2,000 per tick."
  - The diff:
    - computes the observer's coordinate and world index once per pass;
    - precomputes every player's world-entity index once per cycle (`worldEntityIndices`);
    - packs the "was stationary" bit into the sign bit of each 16-bit index, a comment says "so both
      protocol passes avoid a dependent array read".
  - These are classic hoisting and data-packing optimisations, exactly the kind of local rewrite LLM
    search is good at (GUESS).
- **April 2024:** 176.4 → 170.2 ms (see §1.1).
- **Code comments:** −15 to −20% from going branchless; 6–9× in micro-benchmarks from lookup tables
  (§1.2).
- **Search totals** (`gh api search/issues`, 2026-11-08):

  - "benchmark": 0 PRs.
  - "pathfinding": 0 PRs.
  - "player info": 5 PRs (#76, #38, #29, #6, #33) and 9 issues.

## 2. rsmod (rsmod/rsmod)

Repository: https://github.com/rsmod/rsmod (HEAD `fa13b3f6`, 2025-09-30; 1,537 commits).

- **Licence: ISC** (VERIFIED, LICENSE.md: "Copyright (c) 2025 RS Mod"). It is Kotlin and needs "Java
  21 or later".
- **Aim.** VERIFIED: "RS Mod is a RuneScape game-server emulator that aims to be as mechanically
  accurate to the original as possible." Also: "not yet ready for external contributions".
- **Tick loop.**
  [GameCycle.kt](https://github.com/rsmod/rsmod/blob/main/api/game-process/src/main/kotlin/org/rsmod/api/game/process/GameCycle.kt):
  - `preTick()` runs world, NPC pre-tick, player id shuffle, input, route requests, NPC main,
    controllers, player main, logout and login.
  - Then `mapClock.tick()`, then `postTick()`. No timing instrumentation is visible in the cycle.
- **Player info** comes from rsprot (`rsprot-api = net.rsprot:osrs-233-api`, version
  `1.0.0-ALPHA-20250909`). It is called as `service.playerInfoProtocol.update()` in
  `api/net/.../NetworkScript.kt`.
- **Tile pathfinding.**
  [engine/routefinder](https://github.com/rsmod/rsmod/tree/main/engine/routefinder):
  - VERIFIED README: "An efficient [BFS][bfs] pathfinder."
  - A 128×128 search window (`DEFAULT_SEARCH_MAP_SIZE = 128`) and a 4,096-entry ring buffer.
  - Fixed neighbour order: W, E, S, N, then the diagonals. That order sets tie-breaking, so faster
    algorithms must reproduce it exactly.
  - If the target cannot be reached, an "alternative route" search looks for the closest approach
    point within 10 tiles of the target.
- **Pathfinding benchmark** (VERIFIED README; i7-7700K, JDK 11; README present since the repo's
  initial commit on 2024-09-07). One "op" = "calculates 2000 routes sequentially":

  | Route | ms per 2,000 routes (sequential) | µs per route (GUESS: ÷2000) | threadLocal (4 cores) |
  |---|---|---|---|
  | Short (~8 tiles) | 7.429 | 3.7 | 19.010 |
  | Medium (~32 tiles) | 310.479 | 155 | 80.181 |
  | Long (~63 tiles) | 367.350 | 184 | 85.639 |
  | Alt (outside search distance, "forced to iterate the whole search area") | 733.039 | 367 | 168.779 |

- **Harness weakness (VERIFIED code, GUESS consequence).** `RouteFindingBenchmark` runs
  `repeat(routeRequests) { pfer.findRoute(level = level, srcX = srcX, …) }`, the *same* query 2,000
  times on one map. A candidate that caches the last answer would "win". Any AI-search harness needs
  varied, hidden queries.
- **Route tests.**
  - `RouteFindingSimulationTest` runs three real-map cases (lumbridge, barb-village, gnome-maze) and
    checks only the final tile: `assertEquals(params.expectedX, route.last().x)` (VERIFIED).
  - Some unit tests check full waypoint lists, for example "maneuver around through single exit
    point" asserts all 4 waypoints.
  - So exactness is checked partially. A full differential check against a reference BFS is easy to
    add (GUESS).
- **NPC hunt.** `api/hunt` (Hunt.kt, NpcSearch.kt, PlayerSearch.kt) does zone scans around the NPC.
  `NpcPlayerHuntProcessor.kt` adds hunt-rate throttling and skips NPCs with nobody near
  (`isAnyoneNear()`). It uses an injected seeded random (`@CoreRandom private val random: GameRandom`).
  No benchmark exists: the only JMH sources are routefinder and objtx (VERIFIED by search).
- **History.** rsmod has almost no performance commits (git-log grep). Searches found 0 PRs for
  performance, benchmark, pathfinding and "player info"; 1 issue (#26) for performance; 1 PR (#12,
  coroutines) for tick. **No before/after numbers.**

### 3.2 Where the hot paths live in Engine-TS

- **Tick loop.**
  [src/engine/World.ts](https://github.com/LostCityRS/Engine-TS/blob/main/src/engine/World.ts):
  - Per-phase timings go into `cycleStats` (`WorldStat`: CYCLE, WORLD, CLIENT_IN, NPC, PLAYER, LOGOUT,
    LOGIN, ZONE, CLIENT_OUT, CLEANUP, and bandwidth in and out). They are exported to Prometheus.
  - Player and NPC info are computed in `processInfo()`, which carries the comment
    `// TODO: benchmark this?` (VERIFIED).
- **Player and NPC info.** `src/network/rsbuf/*.ts` is a TypeScript port of the Rust rsbuf crate,
  with the same structure (I compared `build.ts` with `build.rs`).
  - Nearby players are found with a spiral over a per-tile grid when the view range has shrunk.

  - `IdBitSet.remove` uses `indexOf` and `splice`, so each removal costs O(n). This looks like an easy
    target (GUESS).

- **NPC hunt.**

## 6. Ranked OSRS-style hot paths (deliverable)

The ranking is by measured CPU per tick at about 2,000 players, single-thread equivalent. The numbers
come from different languages, CPUs and years, so compare orders of magnitude only.

### 1. Player info (who each player sees, plus encoding what changed)

- **Measured cost:**
  - 170 ms per tick on one thread, 11.5 ms on 16 cores (rsprot, 2,046 players, worst case, 2024).
  - 35 ms in Rust/WASM and 86 ms in TypeScript (Lost City, 2,000 players in one map square, 2026).
  - 16–55 ms for sparse layouts.
  - It runs every tick for every player, whatever the players do.
- **Strongest baseline:**
  - rsprot: JVM; cached bitcodes, lookup tables, branchless skip runs, ForkJoin threading with 0.92
    efficiency on 16 cores, plus the PR #76 hoisting.
  - For single-thread compiled code: Lost City's rsbuf (Rust).
- **Harness:**
  - rsprot JMH `PlayerInfoBenchmark`: the rev-242 scenarios, plus the rev-221 teleport-and-chat
    scenario.
  - rsbuf has micro-benches only.
- **Exact check:** yes, but small. rsprot's golden-hex tests (rev 235–242, 2–5 players, including
  multithreaded byte equality) plus decode-back tests. There is no large golden corpus, and nothing is
  compared with Jagex's real client.

### 2. Tile pathfinding (BFS over a 128×128 window, player clicks and some NPC routes)

- **Measured cost per path:**
  - 2.8 µs in native Rust for a 10-tile path (Ryzen 9 3900X).
  - 3.7–184 µs in Kotlin for 8–63-tile paths, and 367 µs when the target is unreachable (i7-7700K).
- **For 2,000 requests in one tick** (the rsmod benchmark's own unit): 7 ms (short) to 733 ms
  (unreachable), single-threaded Kotlin. This is VERIFIED from the README.
- **The real per-tick cost depends on how often players click and how far, which nobody measured.**
  At 400 requests per tick it would be about 1 ms (short Rust paths) to 150 ms (unreachable Kotlin)
  (GUESS arithmetic).
- **Strongest baseline:** 2004Scape rsmod-pathfinder (Rust, ISC). Then rsmod routefinder (Kotlin,
  ISC).
- **Harness:** rsmod JMH `RouteFindingBenchmark` (4 fixed routes × 2,000) and the Rust
  criterion/`main.rs` loop. Both repeat a single query.
- **Exact check:**
  - Partial today: some tests check full waypoints, and the real-map tests check only the end tile.
  - It is **the easiest to make exact**. A route is a pure function of the map, the source, the target
    and the size, so a candidate can be required to return the reference waypoint list exactly
    (GUESS).

### 3. NPC info

- **Measured cost:** 64 ms on one thread and 10.9 ms on 16 cores (rsprot: 500 NPCs × 2,046 observers,
  all saying a line and teleporting). The authors call it "extremely unrealistic"; normal play shows
  10–20 NPCs per player.
- **Strongest baseline:** rsprot (zone search radius 3, top-K selection, cap 149 on Java clients).
- **Harness:** rsprot JMH `NpcInfoBenchmark`.
- **Exact check:** decode-back tests only (8 tests, no golden hex).

### 4. NPC hunt and aggression scans

- **Measured cost:** none per scan. Lost City's production `processWorld`, which contains the
  player-hunt loop, "averag[es] about ~10ms" (the author's statement in an unmerged PR).
- **Strongest baseline:** rsmod `Hunt` (Kotlin; seeded random) and Lost City `HuntIterator`
  (TypeScript; unseeded `Math.random`). Both scan zones, check distance, and optionally check line of
  sight or line of walk.
- **Harness:** none.
- **Exact check:** none. The random target choice needs a seed.

### 5. Zone and entity bookkeeping (counts, zone lists, shared zone buffers)

- **Measured cost:** large only in stress tests and only before fixes, for example "boom 500ms
  faster" (#1095).
- These were O(n²) or recount mistakes, **weak baselines** (T1's warning). They are not good AI
  targets.

### Fit for AI search (GUESS)

- **Pathfinding is the cleanest first target:**
  - a pure function with an exact oracle;
  - a strong Rust baseline;
  - easy hidden test sets made from synthetic maps;
  - but its share of the tick is unknown.
- **Player info is the bigger, better-measured cost:**
  - it has strong baselines and the start of a golden harness;
  - but its cost structure follows OSRS's protocol (the 2,047-slot walk), which Miles's own protocol
    need not copy.

## 7. Evidence against (reported plainly)

1. **Micro wins do not move the tick.** "3op/ms -> 6op/ms … Despite that no noticable improvement in
   the bot test!" (2004Scape `16d9a983`). A scorer must time whole ticks, not kernels.
2. **"Fastest" depends on the scenario and the platform.**
   - Rust/WASM was 2.45× faster than TypeScript when dense, but 3.47× slower when sparse (Engine-TS
     `3febe71`).
   - The Rust pathfinder was dropped for TypeScript because "WASM allocations are performing terribly"
     (`55eccdc`).
   - An AI-found speed-up on one trace can be a regression on another.
3. **Rewrites break subtle behaviour.** The Rust info port was reverted for "breaking observer
   behavior" (`059ffcc3`). Exact checks are mandatory.
4. **Benchmarks are noisy and drift.** Field order alone moved rsprot's benchmark from about 160 to
   200 ms. BENCHMARKS.md is 2.5 years old and no longer matches the harness settings. The pathfinding
   benches repeat one query, which invites caching hacks.
5. **Humans already took the easy wins:** 13.4% (rsprot #76), 2–5× from language ports. T1's range for
   strong baselines (about 0.5–20%) probably applies to rsprot-class code.
6. **The money is small.** Player info at its worst is about 0.28 of one core per 2,046-player world
   (GUESS: 170.23 ms / 600 ms). At T2's €4.94 per hardware thread per month (AX42), that is about
   **€1.4–2.8 a month per world**. A 2× win saves about €0.7–1.4 a month per world (GUESS). The value
   is tick headroom (bigger worlds, steadier ticks), not the bill.
7. **The protocol dictates part of the cost.** The O(N²) slot walk comes from the OSRS client tracking
   all 2,047 players. Changing the protocol (if Miles's client allows it) beats searching for a faster
   encoder of a protocol he does not have to use (GUESS).

## 8. Evidence for

1. The baselines are strong, real, in use and permissively licensed (MIT/ISC).
2. Golden-byte and multithreaded-determinism tests already exist in rsprot (July 2026). The harness
   pattern AI search needs is accepted practice there.
3. Pathfinding has a natural exact oracle, and its implementations exist in Kotlin, Rust and
   TypeScript, which gives cross-checks.
4. The PR histories show people care and keep finding speed-ups in exactly these paths, so the area
   is "live": 40–60 ms, up to 100 ms, 13.4%, 2–5×.
5. No AI-driven optimisation appears in these repositories, so the open-benchmark angle is novel in
   this community (limited to GitHub PR search).

## 10. Open questions

- What share of a full OSRS-style tick is info packets, versus NPC logic, scripts and pathfinding, at
  realistic densities? Lost City's `WorldStat` export would answer this, but no text numbers are
  public.
- How many path requests per player per tick are realistic, and how long are the paths? This decides
  whether pathfinding matters.
- Patent US20100275136: owner, claims, granted or not, expiry date.
- Jagex's position on publishing OSRS-protocol-compatible code in an open benchmark.
- Will Miles's own client use an OSRS-like 2,047-slot protocol? If not, the player-info cost structure
  changes.
- Are Lost City's TypeScript and Rust encoders, and its two pathfinders, byte- and path-identical? If
  so, they give a free differential oracle.
- The rev-242 rsprot benchmark has never been published. It needs measuring on Hetzner hardware.
